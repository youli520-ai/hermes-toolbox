# 经封装层派发的脚本：怎么验才算真验

适用于任何「封装器/插件/派发层 → 脚本」的链路（ha-ctl 派发、cron 调用、插件 exec、subprocess 封装）。这层夹在中间时，**用错调用方式造出的假故障比真故障更常见**。

## 铁律 1：走真实派发链路

验证派发到脚本时，必须用与派发方**完全相同**的调用方式：

```python
# 正确：与插件内部一致
subprocess.run([sys.executable, HA_CTL] + args, capture_output=True, text=True)
```

```
# 错误 1：shell=True 跑命令串——.py 常见 rc=126 permission denied
subprocess.run("python3 script.py", shell=True)

# 错误 2：裸跑脚本——缺派发方注入的 argv/env/编码，行为可能不同
subprocess.run(["script.py"])
```

`rc=126/127` 是**调用层错误**的信号，不是脚本缺陷。先换回正确调用方式重跑，再谈缺陷。

## 铁律 2：改动后验不外溢

只验被改的那条路径不够——被改函数的**调用方**往往更早暴露问题。改完某个函数/分支后，跑 2–3 个**无关**的子命令，确认输出无污染、无 rc 变化。

## 铁律 3：行数异常先回原始层

输出行数与预期不符时，把派发前的**原始 stdout** 逐行打出来与最终回显比对：

- 行数变少通常是**数据变化**（待办被完结、条目被过滤），不是截断 bug
- 拿原始层一比即分清，避免直接去改渲染逻辑

## 铁律 4：测试脚本报错 ≠ 被测对象有问题

验证命令自己失败时，先判定故障归属再决定要不要报缺陷：

| 报错来源 | 归属 | 处理 |
|---|---|---|
| 验证命令语法层（SyntaxError、usage、exit 126/127） | 测试写法问题 | 改测试写法重跑 |
| 被测代码业务逻辑 | 真缺陷 | 修复被测对象 |

高频测试脚本自身 bug：
- `python3 -c "..."` 里 f-string + 嵌套引号转义写坏 → SyntaxError（写成独立临时脚本，或避开嵌套引号）
- heredoc / 管道里 shell 与 python 引号层级混用 → 变量被 shell 先吃掉
- 用 `&&` 串联导致前一步非零时后续静默跳过，看起来像「没输出」→ 拆开逐条跑

判完重跑一次再下结论。把测试脚本的 bug 当产品缺陷上报，会浪费一整轮返工。

## 铁律 5：审查脚本结论前读它的口径

体检/查重类脚本报「缺失 / 很空 / 有重复」前，先确认它**扫的路径范围**：它可能只扫子目录而漏扫常驻文件，口径不同则结论相反。拿脚本结论反推全局判断（如「某 profile 失衡」）前，必须实测真实字符数而不是只信脚本。

同类风险：脚本把目标路径**硬编码指向另一个 profile**，在本 profile 跑出的结论基准是错的。先确认它读的是本 profile 的文件，否则结论不可采信，改用人工核对。
