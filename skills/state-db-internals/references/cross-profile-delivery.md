# 跨 profile 讨论（Discussion / bot_room）的投递取证

适用：多参与方讨论里主人说「检查消息 / 探针」，要判**谁收到了、谁没收到、为什么**。判据只在各 profile 的 state.db 里，日志不是取证面。
边界：本篇只管**讨论话题的跨 profile 定位**；单条探针批次的落库三步取证（标题家族 + ms 收敛）按主技能 SKILL.md 走，两套检索口径不混用。

## 库位置与开法

- default：`/home/agent/.hermes/state.db`
- 其它 profile：`/home/agent/.hermes/profiles/<name>/state.db`
- 只读打开：`sqlite3.connect("file:<path>?mode=ro", uri=True)`；`started_at`/`timestamp` 均为 float **秒**。
- **一个连接只开一个库**，跨库结果在 Python 侧汇总——不存在能连多库的单条 SQL，合并查会得出「查了个寂寞」的 0。

## 取证步骤（按序）

1. **本 profile 定位话题**：讨论取证面以**各 profile state.db 的 `messages` 表**为主（`sessions.title LIKE '%<话题>%'` 只作辅助——标题常与话题的人称名不同）。⚠️ state.db 里的 `hosted_room_*` 系列表恒为空，但**房间事件流真身在 `$HERMES_HOME/shared-state.db`**（events 含消息原文、watermarks 含每成员消费水位）——房间内部 seq/派发机制诊断走 `references/hosted-room-diagnostics.md`，勿据 state.db 空表断「房间无数据」。以 `messages.content LIKE '%<话题原文或消息正文>%'` 为主检索，`sessions.title LIKE '%<话题>%'` 只作辅助——**标题常与话题的人称名不同**（自动生成的 `Group: <slug>`、带 `#N` 轮次后缀、每轮各开一个新 session 故标题还不固定），只按 title LIKE 会漏掉本方已有轮次、更搜不到对方。取首条 user 行的 `timestamp` 作基准 T0。
2. **逐个其它 profile 查同一话题**：各自库跑同一条 content LIKE，记录是否命中、命中 session 数、`min(started_at)`、`max(started_at)`——**按轮次数对比**：本方 N 轮 vs 对方 0 轮，即该话题分发只到一方。
3. **用时间差定因果**：对方首个相关 session 的 `started_at` − 我方**触发动作**（回复落库 / 发出 @）的 `timestamp` ≈ 1～2 秒 ⇒ 该动作是入场原因；差几十秒以上 ⇒ 另有触发源，别把巧合当因果。
4. **查非参与方作边界对照**：第三个 profile 库同话题命中数 = 0 ⇒ 无外溢，分发边界就在参与方内。
5. **上报**：给时间戳 + 库路径 + 命中/未命中，不下无证据的推断。

## 判读规则

- **信封里的参与方名单 ≠ 投递名单**。讨论信封写「one participant with X」只是**创建时声明**的名单；X 侧库里可能一条记录都没有。**禁止据信封断言 X 已收到**——必须查 X 自己的库。
- **ASCII 短词 LIKE 会撞英文词内子串**：`content LIKE '%parity%'` 实测命中一条 `provenance` 的 tool 输出——话题名/编号含短英文词时，命中必须回读 content 确认确为话题正文再计数；中文话题原词（整句中文短语）无此问题，优先用它做检索键。
- **房间身份以信封标题为准，聚合多关键词会串房**：讨论消息的信封头 `[Discussion: "<房间名>"]` 是房间的唯一身份标识。一次检索若 OR 了多个关键词（含别的房间名、编号、短英文词），命中的行必须回读信封标题确认属于**目标房间**再计数——同库常并存多个 Discussion，串进来的邻居命中会让「对方收到了」变成误判。最稳的做法是**只用目标房间名作单一检索键**，需要多键时逐行核对信封，不靠聚合结果直接下结论。
- **同一封信被重复投递 ≠ 多轮对话**：本方命中 N 条 user 行时，先比对各条的 `md5(content)` 与字节长——**全同即同一信封被重复投递**（每次投递各开一个新 session），上报要写「本侧第 N 次收到同一投递、md5 全同」，不能写成本话题在本方有 N 轮对话；对方 0 命中时结论是「**只向本侧重复投递**（单侧派发循环）」，不是「广播不均」。md5 不全同才按多轮对话处理。
- **首条按 @ 触发，入场后按参与方续投**。未被 @ 的参与方收不到首条（静默漏投）；一旦因 @ 建立 session，后续轮次**不再需要 @** 也会投递。想验证这两段，必须设计两组探针，一组结果不能替另一组作答。
- **静默漏投是本类任务的高危点**：对方可能永远不知道话题存在，而话题仍显示它是参与方。我方回复里主动 @ 对方是关掉该窗口的唯一手段（同源规则见 messaging-channels「回复必 @」）。
- **但「我方回复里已 @ 对方」不是投递证据**（上条说的是该做什么，这条说的是怎么验）：@ 发出后对方库仍可能全程 0 命中——@ 是必要条件，分发链路不通时它不生效。判定唯一依据是对方库的命中数，不能因自己发过 @ 就断言对方已收到或「下一轮会到」。
- **日志查不到消息正文**：gateway / gui 日志通常不落讨论标题与消息文本，`search_files` 检索命中 0 是常态。**一轮落空就转 state.db**，不要反复换关键词在日志上耗轮次。
- **时间线要一次取全**：会话与消息的元数据可能在两轮查询之间变化（覆盖复用），锚定候选的首次查询就把 `source/title/started_at/message_count` 与 role 分布一起取回，别分次。
- **结论要能被对方独立复核**：把「库路径 + session id + 时间戳」写进上报，对方在自己侧比对同一组键即可交叉验证，避免两边各说各话。
