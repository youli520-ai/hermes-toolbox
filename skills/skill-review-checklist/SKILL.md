# 技能逐字审查与优化

## When to Use

主人要求**审查、检查、优化一个技能**，找矛盾、重复、漏洞，或要求「提速/模板化/减少思考步骤」时。适用于任何技能（生图、脚本、运维、流程类），不只生图技能。
**新增即审查（2026-08-29 升级为红线级，主人定，强制不可跳过）**：创建新技能、或对既有技能做内容新增（新章节/新分支/新流程）后，必须执行本技能的审查流程（九维快速扫 + 增量清单 + 实跑验证），确认通过后才可使用/登记。**这是红线，不是默认触发**——纯修复、只改数字/文字的小修订可以跳过，但涉及新增逻辑、新建技能、新增脚本/章节时必须过审查，未经审查直接使用或登记即违规。

## 🔴 核心铁律：先验证，后修改（2026-08-28 主人定，第一原则）

**审查中发现任何不确定的事实（数字、路径、口径、范围、行为），一律先实跑验证，确定了再改——绝不凭记忆、经验或文档旧记载下结论。**

- 数字不确定 → 实测（如指令库条数 `list` 数出真实值）
- 路径/软链不确定 → 实测（如 `ls -la` + 实跑）
- 范围/口径打架 → 查代码/脚本实际行为裁决（如解释器铁律范围查 ha-ctl.py 实际调用）
- 行为不确定 → 干跑/复现（如 `_classify()` 干跑验证）
- **changelog /「已修复」「可用」声明是最不可靠的源**（2026-08-28 实战）——修 bug 后必须**实跑被修代码确认**，不能只信 changelog 说「已修」。本会话连抓两个假声明：secrets-manager v1.3.0 声称「修复 secure_read 换行 bug」但代码仍用管道输入（实测读凭据返回空）；hermes-gateway-plugins 声称「hermes config CLI 可用」但实测报 PermissionError。**验证修复 = 跑代码看结果，不是读文档看文字**

- **「跑通」不等于「跑成功」——验证「某事不存在」前，先证明那条命令真的执行了**（2026-10-13 自踩）：`cmd | grep X || echo 无命中` 这类写法在 `cmd` 自身失败时产出**假阴性**——命令不在 PATH、权限不足、参数未实现时，`command not found` 的 stderr 被 `grep` 吞掉 → 不匹配 → 走 `||` 输出「无命中」，**把「命令没执行」读成「查无此任务」**，据此写下并登记的结论会一路扩散（技能正文 + changelog + 注册表 + 三端同步，纠错成本是写入成本的四倍）。**判据**：先看 `cmd` 的退出码与输出长度确认它真跑了，再看 grep 结果；更稳的写法是分两步（`cmd` 存输出 → 在 Python 里搜）。同型风险：**未实现 `--help` 的 CLI 不报错而是直接跑默认行为**（`memory_health.py --help` 直接吐体检报告）——「成功返回」不等于「参数被识别」，验参数要 grep 源码 `sys.argv` 或看行为差异。
- **出处 / 归属同样要实跑验证（2026-10-12 主人纠正补）**：写「主人定 / 主人拍板」标签、在修复理由里加引号引用某条「规则」、或在注册表备注里写「按主人要求」之前，**必须 grep 出这句话的真实来源，并确认它真是主人说的**。文档里某条规则头上带「主人定」标注 ≠ 这条规则出自主人之口——把技能自己长出来的规则说成主人亲口定的，是比「不写理由」更糟的伪背书：主人日后无法判断哪些规则出自他口，也就无法否决本该否决的东西。拿不准归属时写「来源：<技能名> 第 N 行」，不写「主人定」。
- **引用规则前还要核它的适用范围（2026-10-12 主人追问补）**：grep 出规则确实存在只是第一步，接着要判断**这条规则的适用场景覆不覆盖你这次要干的事**。技能里的规则多为解决某一类问题而写，换个场景可能变成反向约束（例：「技能文档路径必须写绝对路径」是为本机查找无歧义，拿它去正当化「改打包分享用技能的路径」就是反向操作——那条场景要的是相对路径）。证据链不完整时把「规则怎么说」和「它适用于什么」分开陈述，别只引前半句。
- **动手前还要确认这个技能归不归我们改（2026-10-12 主人追问补）**：命中 `.bundled_manifest` 的**官方内置技能**（如 hermes-agent、p5js）的 references 一律**不要直接改**——上游同步会覆盖本地修正，本地升版本号也无意义。对内置技能的正确姿势是**审，但不改**：误报落在它身上 → 修扫描器；我家需要补的知识 → 写进自己的技能（hermes-runtime-ops 等）；疑似上游真 bug → 记备案等上游
  - ⚠️ `.bundled_manifest` **不是合法 JSON**（`json.load` 直接抛异常），判定内置只能靠 **grep 命中**，别在脚本里写解析逻辑
  - ⚠️ 上游同步是静默的（只改 mtime、无标记），下游无法区分「我们改的」与「上游推的」；因此**不要**给内置技能单独做 skip 名单——名单是新漂移源，上游一加技能就漏。归属判定要 fail-closed（判不出当内置），并保留只读查询入口兜底
  - ⚠️ 内置技能的「变更时间」来自上游同步而非本人改动，别据此判断该谁负责

**为什么**：审查技能的核心价值就是用「验证过的真」替代「记忆中的旧」。文档可能过时，记忆可能偏差，只有实测是唯一可靠裁决。审 ha-ctl 时「铁律范围」「口令 36+」都是靠实跑确认的——这就是本技能验证的核心。

## 前置（先定主审，再通读全文）

**第 1 步：定主审 profile（2026-08-28 主人定分工）**——审查/改动技能前先确认**归属的主审 profile**，避免三方重复动同一个技能：

| 领域 | 主审 | 说明 |
|------|------|------|
| 生图类技能 | profile-C | comfyui-host-a 等 |
| 影视库类技能 | profile-B | media-library-org、media-tool 等 |
| 智能家居类技能 | 星光 | ha-ctl、windows-ctl 等 |

跨领域或通用技能（如本审查技能）由实际提出需求的一方主审，其余 profile 同步版本即可。

### 跨 profile 内容分叉的合并处置（第 1 步配套，2026-10-16 补）

> 同一技能在三端各一份，常出现**双向分叉**：A 端 SKILL.md 更新了、B 端某篇 references 更新了，**任一端都不是超集**。此时整目录覆盖任一端都会丢内容（对应 skill-library-maintenance 的「整目录覆盖前必查目标端独有文件」）。

1. **先列差异，再分两类**：`diff -rq <A端技能目录> <B端技能目录>` —— 分辨「内容差异」（SKILL.md / references / scripts）与「**运行态差异**」（`config.json`、`.fid_cache.json`、`inspect_result.json`、`file_mapping.json`、`*.bak*`、`__pycache__`、锁文件）。**运行态差异按设计本就各端不同，不参与合并，也不叫漂移**（判据见盲区 #16：先定哪份是真跑的）。
2. **逐文件判方向**：以「谁的内容包含对方」或「谁标注的版本更高」为准（版本高的一方通常已把对方的改动吸收进去了）；判定不出的**挂人工**，别赌（盲区 #16）。
3. **只动文档与共享脚本**：把本端需要的对方更新吸收进来；反向把本端的修正推给对方端时，先确认对方那份确实更旧（内容/版本双向核对，md5 不同 ≠ 更旧），并在汇报里**逐条列出推了哪些文件**——跨 profile 写入要留痕可回溯，禁止静默改别人的库。
4. **收尾**：复跑 `diff -rq` 确认只剩运行态差异 → 落地流程第 7 步同步 → 三端 md5 核对。

⚠️ **文档声明与磁盘现实要对账**：SKILL.md 写「某文件已删除/已迁移」不等于磁盘上真的没有——文件可能被历史操作复活。核到残留时，这本身就是一条 X/E 维发现（文档与磁盘矛盾 + 废弃残留），按待处置项报给主人，别只在心里记一笔。

**第 2 步：逐字通读技能全文**——**必须逐字读完整篇 SKILL.md，再读 `linked_files` 列出的每个 reference**，不要只看开头，更不要只读 SKILL.md 就开始设计。用 `read_file` 或 `skill_view` 拉全文，掌握所有章节结构后再动手。

⚠️ **执行体（`scripts/`、`plugins/`、被引用的 .py/.sh）同样要通读全文，尤其文件头**：改动常常只落在函数体或常量处，而模块 docstring、文件头注释仍写着**旧端点、旧请求头、旧协议、旧凭据名**——只读 diff 改动块，会把这种「同一个文件内部自相矛盾」整段漏掉（审查执行体变更时，先读该文件头部约 40 行 + 全部模块级常量，再读改动块）。

⚠️ **只读 SKILL.md 会重复发明已有机制、或把技能早已裁决过的问题当成新发现**（实测：memory-management 的 SKILL.md 只是入口，`--apply` 自动归档、「每周体检 cron 属后续决策」、「有技能承载不建 L1」这些答案全在其 references/ 里——只读正文时我提了套「三层自动降级」方案，一半是它已有能力，还把已有答案当「待裁决」提给主人）。**判据**：`linked_files` 非空 → 至少读与本次任务相关的那几个；提案里出现「新增 / 建议 / 待裁决 / 目前没有」字样前，**先在 references/ 里 grep 同义词**，确认不是已有答案。references 是深度层，SKILL.md 只是目录——目录不等于内容。

**第 3 步：动执行体前先排并行会话**——同一任务可能被多个 TUI 会话并发处理（state.db `sessions` 按同日 `started_at` 窗口查，出现多条同源任务即疑似；时间列是 epoch 秒，日期字符串 `LIKE '2026-10-29%'` 恒 0 行，须 `cast(<列> as real) BETWEEN <起> AND <止>`，详见 state-db-internals SQL 陷阱）。发现并行即停手报主人只留一个会话再动手——双方同时 patch 同一执行体会互相覆盖，先后 --done 会互清对方的 pending，审查结论互相踩。

## 九维审查清单（2026-08-28 由原五维扩展）

> 原「五维审查清单」2026-08-28 扩展为八维：C矛盾 / R重复 / G漏洞 / T提速 / S稳定 / D红线 / E体验 / X文字（D/E/X 为新增）；2026-09-05 新增第九维 P持久化（载体是否随容器重建/重启存活，与 D 同级——都是「不可逆的静默损失」）。
> 对每个技能按以下 9 类逐项扫描，逐条记录问题（编号归类），不遗漏。

### C — 矛盾（Contradictions）
- 同一文档内**前后声明打架**（如"已注册"vs"实测未注册"）
- 规则 A 说 X，规则 B 说 Y，无优先级区分
- 流程步骤与配套表格/规则不一致

### R — 重复（Redundancy）
- 同一规则在 2+ 处出现（连接失败判断、语言体系、图生图流程等）
- 同一数据/数字分散多处（超分尺寸、端口、强度等级）
- 同一流程在多段重复描述

### G — 漏洞（Gaps）
- 提了错误/异常但没给**恢复/处理步骤**
- 提了概念（如"已注册"）但没给**验证/落地方法**
- 有默认值但缺**例外处理**（如默认 Anima3 与默认 Lv1-Lv2 矛盾）
- 引用文件/脚本但没给**实际路径**
- **缺回滚/撤销路径**（2026-08-28 主人补）：操作做错了/误处理了怎么办？高危操作必须有「撤销/回滚」路径，不只是「异常恢复」。**边界**：S 维「异常兜底」= 系统故障（挂/超时/断连）时的恢复路径；G 维「回滚/撤销」= 操作做错（误处理/误删/误发）时的退回路径——两者别混淆
- **重试次数统一 2 次**（2026-08-28 主人定）：技能调用外部接口（HA/SSH/API）的超时与重试写死为「容错一次=总 2 次」，失败后立即报告，禁止死循环重试
- **机制覆盖面声明**（2026-09-05 主人方案补）：任何声称「自动 / 机制化」的环节，是否同时说明了它**兜不住什么**。正例：env-reminder 的 fail-open（钩子异常回退 agent）；反例：`review_check.py` 自动项只有 9 条机械检查，九维主体仍是人工，若文档不点破这个落差，就是「提了机制、没给边界」
- **文档承诺 vs 脚本实现（2026-10-16 补）**：文档里写成祈使句的操作要求（「须…」「必须…」「记得…」「一律…」），要 **grep 配套脚本确认真的实现了**——文档写了、脚本没做，等于把守卫留在纸上，跑起来必失败（实例形态：文档要求某命令设好可写缓存目录，脚本从未设置，非 root 执行必报权限错）。审查时把文档里的祈使句逐条对照实现核一遍；**同族脱节 = 校验/探测脚本不随实现更新**——那种脚本跑出来的「全不可用」是关于脚本的假结论，不是被测对象的真状态（先跑通验证工具自身，再采信它的结论）。
- **探测路径与运行时路径必须共用同一套常量**（provider 插件高发）：模型发现/可用性探测函数常与请求注入函数各自硬编码不同代的指纹（UA／工具表／端点），上游换代后一条路径活着、一条已死——症状是「定时探测全可用但运行时全 403」或反之。判据：grep 那组常量在文件内的全部引用点，看是否都走同一个 `ACTIVE_*` 变量；验真伪各打一次真实最小请求，并按证据强度分级（200+真实产出=活着；429/503=transient，不断言坏）。

### T — 提速/模板化/减少思考步骤（Templates & Speed）
- 多个决策表可**合并**成一个速查表/主流程
- 重复判断（如"远程主机A是否在线"）可固化成一个**标准命令**
- 工具名/前缀**不统一**（应统一）
- 可把验收标准/规则**模板化**成固定表格
- 可加**主流程速查**串起散落的步骤，减少来回翻页

### S — 稳定性/防错（Stability）【2026-08-26 主人定，重点】
- **入口是否唯一**：主人一句话能否走**唯一入口**定位，而不是多个入口靠脑内判断选哪个 → 减少「用错流程」的出错
- **流程是否自洽**：主流程/分支/异常路径是否环环相扣，不出现「走到某步才发现前面该用另一流程」
- **分支是否明确**：每个分支的触发词/边界是否清晰无歧义（避免"参考图/放大/动起来"等一词多义导致误入分支）
- **分支是否最小化**：每个判断点是否能让默认值自然落位（多数情况少分支），还是让执行者反复权衡
- **默认路径是否清晰**：是否明确「默认走哪条」，无需每次想「这次该不该走特殊分支」
- **异常是否不迷路**：出错/离线/超时/缺配置时，是否有明确的「兜底路径」和「恢复步骤」，而不是让执行者停在原地猜
- **配置是否插件化**：高频变动数据（工作流清单/匹配规则/强度映射/模板）是否**外置配置文件**（JSON/YAML），正文只引用+速览，不内联大表——新增条目/改配置不动正文，提升可维护性，减少正文冗余（如 `comfyui-host-a-direct` 的 `templates/workflows_config.json`）

### D — 红线（Danger/Red-line）【2026-08-28 主人补：必须查】
- **凭据明文**：技能/脚本/文档/配置里是否有完整 token、密码、密钥明文？**必须改为加密库键名引用**（如 `<见加密库 XXX>`），违反即重大失误
- **授权边界**：技能是否检查「谁有权限执行」？会不会被非授权触发（如快路径插件白名单、DM-only）？危险操作是否有确认门槛
- 危险命令防护：技能里是否有 `rm`/`shutdown`/`reboot`/`format`/`drop` 等？是否有确认/回收站/预览前置？删除类操作是否二次确认
- **删除能力的调用链要追到 main()（2026-10-18 实测）**：函数里有确认闸门 ≠ 默认不删——巡检/定时脚本常在 `main()` 里**无条件调用**清理函数（实例：`path-audit.py` 每次巡检都 `rm -rf` 回收站 30 天前目录，没有 `--clean` 开关）。审 D 维时对每个 rm/删除函数 `grep -n '<函数名>(' <脚本>` 列出全部调用点，确认默认路径不执行删除；只读函数体发现不了这层。发现后按 D 维优先级先报主人，**不擅自改另一个 profile 的技能**。
- 红线问题**优先级最高**，发现即停，先向主人报告再动

### P — 持久化（Persistence）【2026-09-05 主人方案新增，第九维】
- **核心判据一句话**：「这个技能今天跑出来的状态和内容，一周后容器重建，还能不能接着用？」
- 现有八维 + 环境核验都假设「文件在磁盘上就是稳定的」，但版本更新/容器重建/重启会丢载体——持久化是**载体是否会丢**，不是文档文字错误，独立成维
- 判据（每条可实测，符合「先验证后修改」）：
  - **P1 关键状态文件是否在持久卷**：核对 `/opt/data/state/`、`/opt/data/logs/` 是否落在已挂载的持久卷（`mount` / `find` 实跑）；不在的列出清单
  - **P2 状态文件是否有自愈能力**：逐一看代码里「文件不存在」时是否兜底。正例：`skill_scan_state.json` 丢→`first_run` 重建基线；反例：`skill_review_state.json` 丢→pending 清单静默消失
  - **P3 脚本/插件本体是否随容器走**：核对 cron 引用的脚本、`~/.hermes/plugins/` 是否持久；已知反例：rtk-rewrite 装系统层 venv 包+软链，重建必丢
  - **P4 是否显式声明「持久化边界」**：文档里有没有写清「哪些持久、哪些临时、哪些重建后要重新灌入」，而不是靠默认
  - **P5 可恢复性**：丢了之后「能自动重建的」和「需要手动重灌的」是否分开标注
- **与 D 同级的原因**：持久化丢失和红线一样是「不可逆的静默损失」（状态没了不报错、不自愈，静默归零），比文字矛盾更致命

### E — 体验（Experience）【2026-08-28 主人补：很需要】
- **通知/输出格式**：技能是否遵守主人通知规范——卡片式（{emoji} {标题} + 分隔线 + 正文 + 🕐时间戳）、全中文（状态值中文化 ok→正常）、不混英文
- **日志与可审计**：技能关键操作是否留痕（审计日志）？出了问题能否回溯？（如 fast-command 审计日志、review 打点）
- **废弃清理**：技能引用的旧脚本/旧配置是否已清理？有没有死引用、废弃条目（记忆规范「废弃即删」对齐）？测试用的临时 cron/脚本测完即清

### X — 文字（Typography）【2026-08-28 主人补：逐字审查的根因】
- **错字/漏字**：别字、笔误、漏字（如「夅克」→「夸克」、「遣派」→「派遣」）——这是必须逐字读全文的原因
- **转义/格式错乱**：引号转义（`\"`）、表格 `|` 错位、反引号游离、双反斜杠乱码——看起来对但渲染/解析错
- **术语统一**：同一概念前后叫法不一（如「指令库」vs「口令表」）
- **时间一致性**（2026-09-05 主人方案补）：文档里所有带日期 / 版本号的声明，是否和 frontmatter `version`、代码注释一致。典型反例：正文 banner 停留在 v1.3.0 但 version 已是 v1.5.0；代码注释「监控 4 项」vs 文档「监控 5 项」
- **标点/排版**：中英文空格、全半角标点、重复段落、head-truncation 重复
- 验证法：`grep` 特定错词/旧引用、`read_file` 逐字读、JSON `json.load` 验证、表格结构核对

### 基础技能高频问题速查（2026-08-28 审 8 个基础技能实战提炼）

> **自动项≠审查通过（2026-09-20 v1.9.3 教训，2026-10-04 补边界）**：`review_check.py` 现有 9 条自动项（4 block + 5 warning），但它们只覆盖**机械可查**的点（版本格式/死引用/凭据/注册表/冗余/堆积/废弃/profile名/mtime），**九维主体仍全人工**——2026-10-04 审本技能实测：9 条自动项**全绿**，人工九维仍查出 5 个问题（白名单数量过时、自审盲区缺失、3 处数字与实际不符）。**自动项全绿 ≠ 审查通过**，不可据此 `--done` 后就认为技能无问题；快扫 done 必须在备注显式写「未人工复核」。
>
> 以下七类问题在多个基础技能重复出现，审查任何技能时**优先扫这七点**（省得逐个重踩）：

| # | 高频问题 | 典型表现 | 修复 |
|---|---------|---------|------|
| 1 | **related_skills 死引用** | `related_skills` 指向已合并/改名/删除的技能（如 lan-host-access、host-a-ctl → 已并入 windows-ctl） | 实跑 `os.path.exists` 核对每个 related_skill，死引用改指向合并后的技能 |

| 3 | **网关运维方式错误** | 文档教 `kill $(pgrep -f "hermes gateway")` + 手动 `gateway run --replace` | 实测 PID 1=node supervisor 托管，改为 `hermes gateway restart`（勿 kill 勿手动 run）；多个技能都有此错（hermes-troubleshooting、messaging-channels） |

| 5 | **读写双向脱敏致误判 / 污染** | ①**读**：`read_file` / `cat` 的输出层会脱敏敏感值——文档里认证头写到密钥变量名时，读出来只剩「Bearer」加三个星号，看着像「截断 / 反引号未闭合 / 内容丢失」，实为完整；②**写**：`write_file` / patch 的**写入内容同样会被过滤**——把「Bearer + 变量名」形态写进文档时会被替换成星号并吃掉紧跟的闭合反引号，造成表格行与反引号错位（静默污染落盘文件） | ①读可疑处必须**字节级核验**（打印 `repr()`、字节码尾段、行长、引号计数）；②写涉及凭据形态的示例时**避开敏感模式**（用「密钥变量名」描述代替字面写法），写完必验反引号配对与表格行结构（2026-09-10 审 hermes-local-admin 双踩：读取误判一次、写入破损一次） |
| 6 | **技能内相对路径 vs 全局共享脚本（假死引用）** | 技能文档写 `scripts/final_log.py` 这类相对路径，实际脚本在 `/opt/data/scripts/` 共享区；死引用检测报「缺失 N 处」，但绝大多数是路径写法歧义而非真死引用（实测 22 处「缺失」里 15 处属此类、4 处真空引用） | 判死引用前先在**三区全盘搜同名文件**（`/opt/data/scripts`、`/opt/data`、`~/.hermes/scripts`，`os.walk` 浅层递归即可）：搜到 = 共享脚本被写成技能内相对路径；全盘搜不到才是真死引用。两类混报会让「缺失」数字虚高，也会漏掉真死引用。⚠️ **改法取决于目的（2026-10-12 补）**：只为消死引用检测噪声、且该技能后续可能打包分享 → **保留相对路径**（绝对路径在无 `/opt/data` 的机器上指空，反使其不可移植）；只为本机直接照文档跑 → 才改绝对路径（配合本表适用范围判定，别一刀切） |
| 7 | **打包分享时可移植性断裂** | `skill_backup_pack.py` 把技能文档里的 `/opt/data/...` 字符串**原样打进包、不改写**——执行体副本确实随包附带，但文档里每条命令仍指本机绝对路径；没有 `/opt/data` 的机器解包后「指路全失据」，执行体是好的、说明书是坏的 | ①不要再往文档里加「本机路径 + 包内路径」双路径——本地确定性与跨机可移植两头不占，读的人还要先判断该跑哪个；②正解是让打包脚本产出**路径对照表**（文档原路径 → 包内 `executors/` 相对路径）+ 一键 sed 替换命令；③配套**「未收进包的引用」显式清单**——被引用但没附带的路径逐条列出，不静默丢弃。⚠️ 收集正则必须放宽到覆盖 `references/*.md`、无扩展名脚本、带参数的路径：只认少数扩展名会**静默漏匹配**，比不匹配更危险（对照表看起来已适配，实则仍失据，给人虚假安全感）。改法判据：能改打包脚本解决的，不动存量技能 |

## 🧠 审查双翼：第一性原理 × 对抗性审查（2026-10-07 主人定，收入评估方法）

> **定位**：九维 / 盲区回答「查什么、查哪里」，本章回答「**怎么想**」——两把思维尺是贯穿九维的**思维方法层**，不占维号（不改「九维」口径）。任何一条九维判据，先过这两把尺再落判定。

### 第一性原理（First Principles）——回到本质，拆掉继承的假设

**一句话**：不问「文档怎么写的」，问「这个技能存在的根本目的是什么、最小必要组成是什么」——凡是回答不了「删掉它会怎样」的规则，都是继承来的假设。

| # | 判据 | 操作 |
|---|------|------|
| F1 目的追溯 | 每章节/规则能否回答「删掉它，根本目的会受损吗」 | 答不出 → 冗余候选（记 R 维） |
| F2 假设显性化 | 规则背后的隐含假设是否写明且验证过（如 mtime=内容新旧、changelog=已修、自动项=全检） | 未验证假设 = 高危漏洞（历史事故多源于此，见高频问题#5、盲区#7） |
| F3 从零重建 | 今天从零设计，还会写出这个结构吗 | 不会 → 演化包袱而非本质结构（记 T/S 维） |
| F4 还原到事实 | 规则冲突/存疑时，裁决依据是文档惯例还是**实跑事实** | 一律实跑——与核心铁律「先验证后修改」同源，是第一性原理的落地形态 |

### 对抗性审查（Adversarial Review）——站在破坏者一侧主动找茬

**一句话**：不问「它写对了吗」，问「**我怎么才能让它出错**」——构造反例攻击技能，防守得住的才算通过。

| # | 判据 | 操作 |
|---|------|------|
| A1 输入攻击 | 造边界/歧义输入（触发词重叠、含糊措辞、参数越界） | 命中 2+ 分支或落空 → B1/B3 缺陷 |
| A2 误用攻击 | 假装只读了速查表/第一屏就上手，会怎么用错 | 能用错 → 入口/默认路径缺陷（记 S 维） |
| A3 声明质证 | 逐一质证「已修复/已注册/自动/全绿」类声明，要求证据（实跑输出/行号/md5） | 拿不出证据按不可信处理（对应核心铁律「changelog 最不可靠」）；**攻击对象包括你自己刚写进方案的事实声明**——自己写的更要逐条核，结论对而证据错同样会被戳破（本轮自审方案时一条证据就弄错了，还差点据它改错地方） |

**A4 失败注入要覆盖的最常见场景**：上游/同步操作**静默改写文件**（只动 mtime、不留标记）时，下游以「文件变了」为唯一信号的机制会全部误触发。此时判定信号错了——"文件动了"代理不了"我们需要负责"，正确代理物是**变更的作者是谁**。攻击这类机制就问一句：这个变化是我方造成的，还是上游推的？

**执行约定**：

⚠️ **#3 凭据扫描是半可机化，单跑正向会同时藏住误报与漏报**（实测双向都出过，动它之前必读）：
- **误报**：教学文档的占位符（`ghp_xx...xxxx`、`your-key-here`、`<your_token>`）与描述性英文句子（"the returned secret"、列举 `` `token=` `` 的行）会被当成候选，人工在假阳性上空耗判断力——扫描器须识别占位指征与说明文字。
- **漏报更致命**：形如 `<键名>: <24位字母数字混合串>` 与 `<键名> = <函数调用>()` 同为 `[A-Za-z0-9_]+` 形态，靠「右侧是纯标识符就是变量名」区分时，**真凭据会被吞掉**（实测 9 条真凭据漏 6 条）。判据要用熵：够长且数字密集、或大小写与数字混排 = 随机串；短的可读驼峰才是变量名。
  - ⚠️ 本文示例写"字母数字混合串"而不写真值字面量：技能正文里的凭据形态示例同样会被凭据扫描器命中，写具体值等于自己制造候选（本位即实例）。
- **规则顺序会遮蔽新逻辑**：多分支谓词里，新加的熵判据若排在原有早退规则（`^\w+$` 之类）之后，永远执行不到。改这类函数先通读全部分支的 `return` 位置，再决定新规则插在哪。
- **改完必须成对跑测试**：一组「须排除」的假阳性 + 一组「必须仍报」的真凭据，两个方向都过才算改对；只验证假阳性降下去，会顺手把这条红线关掉。
- 已知边界（非缺陷，汇报时注明即可）：值含 `@`/`$` 等符号时正则整条不命中，属覆盖率限制。

⚠️ **#8「profile 名过时」的判据要按「指向 profile」收窄，否则主机名会被误报（2026-10-12 修）**：原判据对技能全文做 `\bhost-a\b` 匹配，而**远程主机A那台主机的档案文件也叫 `host-a.md`**（`/opt/data/memory/default/`，与 profile 同名不同物）——主机名、`host-a_ctl`、`host-a-download` 这类工具名都会被当成旧 profile 名刷 warning。正确判据只认**指向 profile 路径/目录**的形态：`profiles/host-a`、`profile … host-a/skills`、`host-a/skills` 等。改完必须**双向测试**：一组真旧名（`profiles/host-a/…`）仍须命中，一组主机/工具名必须不命中——只验单向会把另一侧的红线或噪声关掉。

⚠️ **#9「mtime 污染用法」的「裁决」二字只指内容与方向，不指新鲜度（2026-10-12 补边界）**：`getmtime` 用来判断某个文件**是否过期**（如读 delta 文件先看 mtime 是否超过 12 分钟）是**正确设计**——新鲜度裁决天生就该用 mtime；只有拿 mtime 当「内容是否变化」「谁新谁覆盖谁」才是污染。审查时看到 `getmtime` 先分清它服务哪一类判据，别一律升级成问题。

⚠️ **判据改进标准 ≠ 检测器改完，误报会照常产出**：上条边界已写进本清单，但实跑 `review_check.py` 仍输出 `mtime 污染用法: getmtime 无 md5 裁决兜底`——判断 #9 是否真污染要看**扫描器当前行为**，不是看本清单写没写（核心铁律「changelog / 已修复声明不可靠，实跑才算数」在「标准-脚本契约」上的形态：本清单是标准源头，它写了但 `review_check.py` 没跟 = 同一条铁律的受害者）。处理顺序：① 按上条边界判是否真污染（getmtime 服务的是过期判定 → 误报）；② 误报 → **修 review_check.py 的 #9 实现**，不要去改被审文件的 getmtime 用法（盲区 #7 同理：误报落在谁身上，就修让误报产生的那一层）；③ 汇报写明「判据已入标准、检测器未跟」，别只说「已确认误报」，否则下个审查者会从头重查一遍。⚠️ 未逐行核过被审文件的 getmtime 用法就只称「**推定**误报」，要写死结论先按 A3 质证自己这条判断。
- **官方内置技能（命中 `.bundled_manifest`）的 references 不要直接改**——上游同步会覆盖本地修正；误报落在它身上时，正解是修扫描器让它不再误报，而不是改被误报的那份文档。

⚠️ **#2 只读顶层 `related_skills`，看不见 `metadata.hermes.related_skills`**：多数技能把 related_skills 写在 `metadata.hermes:` 下，而扫描器只读 frontmatter 顶层 ⇒ 恒报「未声明」（假阴性）。看到「未声明」必须人工再读一遍 frontmatter 的 metadata 子树再下结论；修法是让扫描器两层都读（顶层优先、metadata 兜底）。

   - 非白名单技能（profile-C独有 yao-anima3-prompt-templates、profile-C上游 comfyui-host-a-direct）**不自动推送**，按需人工/跨 profile 吸收
7.5. **🔴 改内容必升版本（2026-09-06 主人定，机制改造带来的强制规则）**：**任何技能内容变更，无论多小（错字、补说明、references 更新），都必须升版本号（哪怕 PATCH +0.0.1）**。原因：skill_sync 方向裁决已重构——版本相同但内容不同 → **挂人工拦下、不自动同步**。这是故意设计的安全网（防反向覆盖），不是 bug。**不升版本的「偷偷改」会被同步机制卡在挂人工**。三个 profile 使用者须知：改内容 → 升版本（PATCH/MINOR）→ 登记注册表 → 三端同步；若发现改了内容没同步、又没升版本，是安全网在起作用，应去升版本而非困惑
8. **验证**：grep 检查残留矛盾声明、残留旧引用、版本号、关键章节齐全；配置 JSON 用 `json.load` 验证

## 脚本位置体系（2026-08-28 主人定：三区 + 技能文档索引）

**核心原则：技能脚本能放技能目录（`skills/<name>/scripts/`），但不能一刀切**——被 cron/daemon 引用的脚本必须路径稳定（容器重启不丢），随技能迁移会断链。位置混乱的根源是「运行性质」与「功能归属」两个维度混为一谈。

### 三区定位（按运行性质分）

| 区 | 路径 | 放什么 | 典型 |
|----|------|--------|------|
| **核心区** | `/opt/data/*.py` | 统一入口的执行器、常驻主脚本 | device-ctl.py、watch_main.py、lib_*.py、review_*.py 等统一入口执行器（示例） |
| **服务区** | `/opt/data/scripts/` | 独立工具链/服务，被技能 SKILL.md 引用 | nas-tool、feishu_card.py、cron_notify.py、sweep*.py、cloud-prep.mjs |
| **调度区** | `~/.hermes/scripts/` | **只放 cron 脚本**（watchdog/monitor/cleanup/watch），唯一真相 | status_watchdog.py、host_monitor.py、cleanup_watch.py、review_collect.sh（示例） |

### 技能文档索引（识别率的真正来源）

- **识别率靠「技能 SKILL.md 里的执行器索引表」，不靠目录分层**——路径就算平铺，只要每个技能文档列一张「本技能脚本 → 实际路径」表，找脚本时 `search_files` 按技能名一搜就到
- 每个技能 SKILL.md 必须含「配置文件/脚本索引」节（如 ha-ctl 的「配置文件」表、windows-ctl 的「配置文件」表）
- **找脚本流程**：主人说某功能 → 定位技能 → 看 SKILL.md 索引表 → 拿绝对路径，不再临场 search 全盘

### 存量不动 / 新增归位（2026-08-28 主人拍板）

- **存量脚本不搬**：现有三区平铺脚本维持不动（迁移会断 cron/daemon/文档路径，高风险）
- **新增脚本**：按三区定位落位 + 在所属技能 SKILL.md 索引表登记
  - 被 cron/daemon 引用 → 调度区/核心区
  - 纯技能逻辑、手动触发 → 优先 `skills/<name>/scripts/`（随技能走，可复用、可跨 profile 同步）
- **同一功能脚本只放一处**：新增前先 `search_files` 查是否已有同名/同功能脚本 → 有则复用/合并，无则按三区落位
- **技能文档路径必须写绝对路径**，且与实际一致
  - ⚠️ 2026-10-12 主人追问后补「适用范围」：此条的动机是**本机查找无歧义**（定位技能 → 看索引表 → 直接拿路径，不再临场 search 全盘），**不是跨机可移植**。两种口径冲突时要分清：
    - 本机直接照文档跑 → 绝对路径（跳过"猜它在哪个区"）
    - 打包分享给无 `/opt/data` 的机器 → 绝对路径会指空，须按 `skill_backup_pack.py` 产出的 dependencies.md「五、路径对照表」改指向包内副本
  - ⚠️ 归属更正（2026-10-12）：本条曾被误记为「主人亲口定」。实际出自 2026-08-28「脚本位置体系」章的成文，动机如上；**本节内哪些条是主人定、哪些是当时自补，未经逐条核对**，见 SKILL.md changelog v1.12.1

## 主入口唯一性四判据（2026-08-28 主人定）

> **核心一句话：主人同一句话，是否要凭脑内判断选走哪条路，而不是天然落到唯一的入口？**

| 判据 | 判断法 | 反例（不唯一） | 正例（唯一） |
|------|--------|--------------|-------------|
| **P1 平级路径** | 同一意图是否有 2+ 条「平级」（无主次）路径可达 | 调风扇风速：「风扇开大点」走引擎2 vs「风速调 70」走引擎1.5 | 无论措辞都落同一指令库/中文名映射 |
| **P2 自明性** | 是否需要靠「记忆/经验」选路，而非指令本身自明 | 「看主机状态」——远程主机A还是远程主机B？得记「远程主机A=桌面机」 | 「远程主机A状态」「远程主机B报表」指令名自带主机 |
| **P3 同流性** | 不同措辞是否落「同流程不同参数」而非「不同处理流程」 | 「关远程主机B」高危拦截 vs「关宿舍电脑」放行，说「关电脑」易入错 | 所有「开/关/查某设备」走同入口，仅参数不同 |
| **P4 默认兜底** | 主人含糊说话时，默认落哪条是否清楚 | 技能没写「默认走哪条」，执行者猜 | 明确「普通主题走 ①③⑤，特殊才走 ②④」 |

**一句话速判**：把主人原话丢给两个人，选的路不一样 = 入口不唯一；或：主人需要我反问「您指哪个？」的地方，就是入口不唯一处。

## 分支四判据（2026-08-28 主人定：分支与分支的重复/多余判断）

> 主入口是「进哪条大路」，分支是「大路里的岔口」。分支审查比主入口更细——判断分支之间是否**重复、多余、依赖不清**。

| 判据 | 核心问题 | 判断法 | 问题信号 |
|------|---------|--------|---------|
| **B1 正交性**（互斥且完备） | 分支是否重叠？输入是否只落一个分支、且所有情况都有归宿 | 造一个输入，看能否命中 2+ 分支；有无输入落空 | 同一输入命中 2 分支 = 重叠/歧义 |
| **B2 必要性**（真分叉 vs 为分而分） | 两个分支的处理逻辑是否真不同？还是仅触发词不同？ | 看两分支的**落点代码/命令是否相同** | 落点相同 = 多余，应合并成「一分支+多触发词」 |
| **B3 主次兜底** | 是否有明确默认分支 + 兜底分支？顺序是否清晰？ | 从分支列表往下走，最后是否「兜底捕获一切」 | 平行无优先级，或漏兜底（输入不命中任何分支怎么办） |
| **B4 传递依赖** | 分支间是否有 A→B 转交依赖且已标注？ | 追踪每分支「出口」——是终结还是转交下一分支 | A 处理完还要交给 B，但文档没写，执行者以为 A 独立完成 |

**运用**：审查任何技能，对每条分支路径逐条过 B1-B4。分支理顺后，入口自然唯一（重叠分支 = 伪入口）。

## 增量变更审查清单（2026-08-28 主人定：只新增/合并部分时用）

> 完整审查走九维全量；**增量变更（新增/合并某部分）** 至少补以下**六项**，防止「只审表面、漏查关联」：

1. **查依赖（A 三则，2026-08-28 主人补）**：
   - **引用不动不查**：引用的脚本/配置/技能没被改动 → 不查（省成本）
   - **引用需改必查**：引用的对象要改 → 必须查它引用谁、谁引用它（grep 其他技能/脚本/文档是否指向被改位置）
   - **无必要少引用**：能不引入新依赖就不引，控制耦合（⚠️ 2026-08-31 补：**增量可查、存量全盲**——新增时能当场 search_files 查重；但「引用不动不查」豁免存量，已有冗余引用（如 ha_control.py 双份）除非恰好被改动否则永不进审查视野，须靠「审查盲区」#1 主动核对）
2. **查入口收敛**：这次变更是**让入口更唯一，还是又多出一条**？新增入口必须同时确认它成为该诉求的唯一入口
3. **查源自洽**：合并进去后，源技能**主流程是否变乱**、references 是否仍有序（不越堆越多找不到主线）
4. **查同分支重复**：新增的分支与既有分支是否 B2 落点相同（重复）、B1 触发词重叠（歧义）
5. **查验证实跑（B 验证，2026-08-28 主人补）**：涉及状态文件/缓存/数据源的改动，验证**必须实际跑一遍**（写进文档不算，要真执行确认结果），如 pin_check、dryrun、接口连通性实测
6. **查存量冗余（2026-08-31 主人补，破「引用不动不查」豁免）**：增量变更顺带核对被引脚本/技能在磁盘是否唯一——同功能双份、版本堆积、废弃残留（见「审查盲区」#1-#3）都是存量问题，审查文档时引用的对象存在不代表磁盘上没有第二份

| 11 | **上游静默改写被当成我方变更（2026-10-12 新增）** | 上游同步/重装/解包会改文件 mtime 但不留「谁改的」标记；pending 机制只问「文件变了没」，不问「归不归我们管」→ 官方内置技能的每次上游同步都变成一条人工待审 | 三层分流：**归属判定**（grep `.bundled_manifest`，判不出按 fail-closed 当内置）→ **处置分流**（本地技能走原逻辑；内置技能只跑自动审查、无问题则静默记录，**不写 pending**）→ **提醒只报本地技能**。修在最上游的 collect.py 归属判定，不在下游 review_check 过滤——否则 `--status` 与便签数字会对不上。红线「技能必审查」不冲突：内置技能仍跑自动审查，只是不占人工待办位 |

## 优化原则（提速核心 + 稳定兜底）

- **减少思考步骤**：主人一句话 → 主流程速查（5 步）→ 一步定位通道/工作流/强度/确认，别让主人在 4 个表间跳
- **标准命令**：反复判断固化成一条命令（如远程主机A在线速查一条定生死）
- **模板化**：验收标准/匹配规则固化成固定表格（如故事分镜验收速查 4 项）
- **脚本模板化，不临场拼代码**（2026-08-28 主人补，总原则）：**有重复需求的操作一律用现成脚本/模板执行，绝不自己临场拼代码**——重复性操作先找有没有现成脚本（`search_files` 查三区），没有则固化一个模板脚本再执行。根治每次手拼出错、路径混乱、逻辑不一致
- **固化责任前移**（2026-08-31 主人补）：插件化/模板化/去重**不等审查发现**——主人重复说同一功能 2 次以上，执行时就顺手固化成配置/脚本/模板，别拖到审查才想起（审查对这类问题天然盲区，见「审查盲区」节）
- **统一入口**：任何任务先落「生图决策主流程」这唯一入口，再进分支；不因主人措辞不同而换入口
- **默认优先**：明确「普通主题走 ①③⑤，特殊主题才走 ②④」，多数情况不碰分支，减少错误
- **异常兜底**：每个失败点给「恢复路径」（如 MCP 挂了 → 拉起来；远程主机A探测不到 → 走 A2A 问星光核实）
