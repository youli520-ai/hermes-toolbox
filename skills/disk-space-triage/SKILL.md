# 磁盘空间定位与清理方案

给主人报磁盘空间告警、或自己要找空间时走这条线。**本技能只负责「定位 + 出方案」，执行删除必须主人点头**（红线）。

## When to Use
- 监控/环境便签报「磁盘 /：85%（越限）」这类水位告警
- 主人说「磁盘满了 / 空间不够 / 清理一下 / 看看空间」——「看空间」与「清空间」走同一套流程，**先定位后请示**，不要拿到请求就开删
- 要找地方放新东西（大文件/备份/镜像），需先知道哪块盘还有余地

⚠️ 本技能跑在 shell 环境：`du`/`df`/`ls -1` 是主力工具，**不要用 search_files 代替 `ls -1`**——那是一次要列全目录条目名的场景，按模式匹配的文件工具给不出目录清单。

## 1. 先把容器路径映射到宿主卷，否则会清理错盘

**这一步不能跳。** 容器内 `df -h /` 报的是底层宿主卷；在容器里跑 `du -sh /*` 得到的「占用 TOP」会把**另一个卷**上的内容算进来，于是会把一块还剩 865G 空闲的盘当成元凶去清理。

```bash
# 容器路径 → 宿主卷的真实归属
grep -E " <路径> " /proc/self/mountinfo
findmnt -T <路径> | tail -1        # 直接看 SOURCE：同一设备同一子卷才算真的占告警盘
df -h | grep -vE "overlay|tmpfs|shm"   # 看有几个独立卷、各自水位
du -xh --max-depth=1 / 2>/dev/null | sort -rh | head -20   # -x = 只算当前文件系统，跨挂载子卷不计入
```

⚠️ **认准告警盘之后，下钻时仍会重新踩回别的盘——`du` 默认跨文件系统。** 挂载拓扑已经确认，不代表后面每一步都安全：对父目录做 `du -sh <父>/*` 会把子卷（独立挂载点）整个吞进来，于是 TOP 里的大头其实在另一块盘上（实测把 932G 数据盘上的 21G 音乐、2.9G backups、645M 安装包当成 180G 告警盘的候选，连报两轮才被主人点破）。判据只有一条：**每个候选再单独核一次设备**，与告警盘的 Filesystem 不同就整项剔除，别让它进清理清单。

```bash
du -x --max-depth=1 <父> 2>/dev/null | sort -rn | head    # -x 不跨文件系统，一次性排除所有子卷
for d in <父>/*/; do
  dev=$(df "$d" | awk 'NR==2{print $1}')                  # 与告警盘 Filesystem 比对，不同即剔除
  echo "$dev  $(du -sx "$d" | cut -f1)K  $d"
done
```

判读：`/opt/data` 与 `/` 同卷 → 它们的占用**合并**计算；而 `/opt/data/<某子目录>` 若单独成行且挂载源不同 → **那是另一块盘，它的大小与当前告警无关**，须在结论里显式排除，别让它出现在清理清单里。

⚠️ **告警自带的清理建议也要过一遍挂载验证，照抄会白干。** 便签/监控里「`du -sh /* | sort -rh` 清理根分区大文件」这类模板命令指向的常常是**另一块水位健康的卷**——本机 `du` 榜首是 `download/` 22G，而它挂在独立的 932G 分区上（8% 使用率），跟告警的分区毫无关系。**先验挂载归属，再决定听不听建议。**

⚠️ **⚠️ 同一台 NAS 上可能同时挂着多块物理盘（这是「清理错盘」的完整形态）**：本机实测系统盘 180G（88% 告警）与数据盘 932G（音乐/下载/备份/comfy_output 各子卷，8%）并存。在数据盘的目录里 `rm` 掉 1.578 GiB 探针产物，**`df` 一个数都不动**——文件真实删除了，但删的不是告警的那块盘。判定口径只有一条：`findmnt -T <被测路径>` 的 SOURCE 与 `df -h /` 的 Filesystem **同设备同子卷**，才算真的动到了告警盘；仅凭「路径在容器里可见」「路径是 /opt/data 的子目录」都不算。

⚠️ **清理后第一件事是复验 `df`，两个数对不上就停下来查归属**：`du -sh <被清目录>` 降了、`df -h /` 没降（或降幅差一个数量级）时，**不要把「释放 X G」当成成果汇报**——先查挂载源，确认删的是哪块盘。确认删错盘就照实说「已释放 X，但告警盘水位不变」，再回到 §1e 单独报那块盘上真正能动的大块。

⚠️ **子卷可能嵌在告警卷的路径内部**：`/opt/data/music` 这种独立挂载点，是 `/opt/data`（告警卷）的**子目录**，却在 `df` 里单独成行、挂载源不同——它占的是另一块盘的空间，**与告警卷水位无关**，但 `du -sh /opt/data/*` 会把它整个吞进去。对账时须 `--exclude=<子卷名>` 后再求和，否则「可见合计」被虚高，1b 的差额结论跟着错。`df -h | grep -vE "tmpfs|shm"` 里每一行都要跟告警卷的挂载源比一次，别只看顶层。

⚠️ **`--exclude` 加完必须验证总量真的降了**：`--exclude` 按遍历到的条目名匹配，给嵌套子目录传绝对路径常常一条都不生效（实测排除前后 `du -sh` 都是 23G，排除形同没写）。判据只有一条：**对比排除前后的总数，没降就是这个 exclude 没命中，改 cd 进父目录用相对条目名再跑**，别拿一个没生效的排除值去做后面的对账与清理合计。

### 1b. 先对账：`df` 已用 ≫ 可见文件之和 → 有看不见的黑洞

把 `df` 的 Used 与容器内可见文件的总量对一次账：

```bash
df -h / | tail -1                      # 记下 Used
du -sb --exclude=<其它挂载点> /* 2>/dev/null | awk '{s+=$1} END {printf "可见合计 = %.1f GiB\n", s/1073741824}'   # 容器内可见总量
```

⚠️ **必须用 `-sb`（字节）不能用 `-sh`（人类可读）配 awk 求和**——`du -sh` 输出的 `41G`/`363M`/`1.2K` 是**带单位的字符串**，awk 会把 `41G` 按数字 `41` 取值、把 `363M` 当 `363` 加进去，混算出的和**与真实字节数毫无关系**（实测同一目录：`du -sh` 汇总得 `1590.2`，`-sb` 真值 `2.5 GiB`，差 600 多倍）。对账的数字必须站得住，否则整个 1b 节结论跟着错。

⚠️ **同一个单位陷阱会在你自己写的扫描脚本里再犯一遍，而且更隐蔽**——`st_size/1024/1024` 后面手工贴个 `G` 字样，得到的数字看着合理（实测把一个 29M 的包报成 `28.6G`），足以让你兴冲冲地宣布「清出 49G」而实际只清出 29M。**凡是要报给主人看的体积，来源必须是某条真实命令的输出**（`du -sh` / `ls -lh` / `df`），自己换算出来的值先用 `du -sh` 复核再出口。报数与实测差出一个数量级时，先怀疑换算，而不是先报喜。

**差额巨大（本机 152G 已用 vs 2.5G 可见，约 150G 缺口）→ 缺口在容器可写层（overlay upperdir）。那一块在容器内既看不见也删不掉，不是容器侧能 reclaim 的空间。**

此时**不要**去堆清理动作：可见文件全删光也填不上这个洞，主人看到的是「清了半天还是 85%」，反而像没干活。**先报这个结论**，再把可清项当「缓解」而非「解决」来提。真正的解法通常是把冷数据挪到另一块有余量的分区，属结构性调整，须主人点头。

### 1c. 先算候选总量占比——清理量是噪声级别就别执行

扫完目录得出候选清单后，先把它们的总量加起来与分区已用量比一比（`df` 的 Used vs 候选合计），再决定要不要请主人批准。**一批看着「20 个文件、四个类别」的候选，加起来可能只有 50M**，对着 152G 的分区是噪声——执行完 `df` 一个数都不动，主人却要为「什么都没发生」付一次授权和一次期望。

规矩：**清理量不足已用量的约 1% 时，先直说「这批清完水位基本不动」，再问主人要不要为它走一遍授权流程**；不要把一串删除动作演成一次「空间已回收」的成果汇报。删除本身没错，错的是让它看起来像个解决方案。

配套：§1b 的黑洞存在时，正确的结论是「清理只是缓解」——而**缓解也要有量级感**，「缓解 50M」和「缓解 5G」不该用同一种措辞汇报。

### 1d. 同 inode 的重复路径会让 du 双算——删一处不省空间

`du` 按路径走，两个路径指向同一 inode（硬链接、绑定挂载、同一目录的两个入口）会被算两遍，清单里就出现「同一份数据的两个可删项」。删掉其中一个，`df` 纹丝不动，主人会以为清理没生效。

```bash
stat -c '%i %n' <路径A> <路径B>      # inode 相同 = 同一份数据
```

判出同号就在清单里显式标注「A 与 B 同 inode，删一处不省空间」，并把该组按**一份**计入合计，不要按两条路径相加。

⚠️ **同一个 btrfs 子卷挂到两个路径也是同一种双算**，且更隐蔽——它不表现为两个疑似副本文件，而是「父目录的 `du` 把同一个子目录吞了两遍」，于是 `du -sh <父>` 报的 TOP 里同时出现两份 2.9G，看起来像顺手能省一笔，实际只占一份。发现与确认：

```bash
findmnt -T <路径A> ; findmnt -T <路径B>   # 挂载源相同 = 同一子卷的两个入口
stat -c '%i %n' <路径A> <路径B>            # 同号即同一 inode（与硬链接判据一致）
```

确认后从合计里剔除重复的一份，并在结论里写清「这是两个挂载点不是双份数据」，否则主人会按虚高的总量做决策。

### 1e. 两根杠杆分开报：删除 vs 跨卷迁移

候选合计只是噪声时（§1c），别急着收工——先看看有没有**能整体搬到另一块有余量卷**的大目录（冷数据、媒体库、归档）。删除和迁移不是同一种动作，得分开报：

| 杠杆 | 动作 | 对水位 | 请示方式 |
|---|---|---|---|
| 删除 | 清单点名的废弃项 | 常只有几百 M～几 G，噪声级 | 逐项列清单 |
| 跨卷迁移 | 整目录搬到空闲卷 | 唯一能让 `df` 明显动的一项 | **单独请示**：迁还是留，落到哪个卷/目录 |

**迁移只挪不删**，主人要的是数据还在、水位下去，所以不能混进「可删」清单里一起批。报的时候给两行合计：「纯删除约 X（占已用 Y%）」「若加迁移 Z 则约 X+Z」，让主人一眼看出哪根杠杆才值得走一遍授权。

### 1f. 先给每个大头补一个「生长趋势」维度——它直接改变处置建议

TOP 占用的下一步不是直接进删除/迁移清单，而是各补一条趋势判据：**这个目录还在长吗？**

```bash
find <目录> -type f -newermt "2026-09-01" | wc -l    # 阈值取 4～6 周前；0 = 停止生长
```

判读直接改变建议的分量：**不在长的目录，风险最低、也最该先谈迁移/归档**（它是历史包袱，往后只会一天比一天难搬）；**还在长的目录，只清存量治标**——要一并提示要不要先停生成器，否则下个周期又长回来（§4 同一逻辑）。

同一维度也用于**媒体库类大头**：给「文件数 + 各格式分布 + 最近一次写入时间」三个数，比只报一个 21G 有用得多——文件数与格式分布决定了它有分别整（按专辑/分类归档）的可能，最近写入时间说明它是活数据还是死数据。

## 2. du 要收敛着跑，宿主卷会超时

- **先 `ls -1` 再 `du`**：目录数量级未知时直接 `du -sh <目录>` 在大卷上可能跑几分钟无输出。
- **逐层收敛**：`du -sh <父>/* | sort -rh | head` → 只对 TOP 几名下钻，不对整棵树一次展开。
- **别跨挂载递归**：父目录的 du 会把子卷一起吞进去，既慢又重复计数；子卷单独算。
- **长任务改后台**：`terminal(background=True, notify=True)`，别用前台大 timeout 硬等（前台上限 600s，超了转后台反而丢结果）。
- **顶层扫完若大头在**容器看不到的地方**（宿主 `/vol*`、`@` 开头目录），到此为止**——那不是容器侧能 reclaim 的，转第 5 节。

## 3. 分两段产出：容器内可回收 / 宿主侧需提权

结论必须把两类分开列，混在一起会让主人以为「全都能清」：

| 段 | 内容 | 谁执行 |
|---|---|---|
| 容器内可回收 | 探针测试产物、一次性备份、残留 tmp、轮转旧日志 | 主人点头后 agent 可直接做 |
| 宿主侧需 root | 卷级快照、副本目录、docker 层、宿主应用数据 | 需 NAS root 通道，且逐项确认语义后才动 |

**每项标大小**，主人按大小决策；只报总数等于让主人重新扫一遍。

宿主侧 Docker 对象（镜像/卷/构建缓存）的盘点命令、汇总口径陷阱与清理安全边界见 `references/docker-object-audit.md`——🔴 报任何 reclaimable 数字前必须逐项核对（实测卷汇总报 5.14GB、逐项合计仅 117MB）。

## 4. 容器内稳定积累的「可回收」类别

这几类每次探针/测试/迁移都会再攒一批，是清理时的默认候选（**仍须逐项列出，不自动删**）：

- `*probe_data.bin`、`*probe_*.png` 等探针产物——探针已结束即纯垃圾

⚠️ **但「探针已结束」得先验，别默认**。这类文件常是某个定时/自检任务按批次反复生成的，主人以为跑完了、目录里其实每天还在长。删除存量前先给主人这三个数：**份数 + 起止时间跨度（最早/最新 mtime）+ 占用合计**，并明说「只清存量的话下一轮还会长回来，要不要先停生成器」。**同 MD5 的多份是同一载荷存了 N 遍**，报一行「N 份 / 同一哈希 / 合计 X」就够，逐份列没有信息量；哈希全同时核验或处置结论只做一次。
- 一次性状态库/配置备份：`*.bak-<日期>`、`*.bak-*`、`*.orig`——留最近 1～2 份即可
  - ⚠️ **一次修复留一份的历史备份要逐个问「还回得去吗」**：形如 `state.db.bak-webui-lockfix`（某次故障修复前的快照）、`ui-dist-<日期>.tar.gz`（某次前端改版前的打包）。这类文件每份几十至几百 M，命名带日期与事由，看着可删；但**有的正是某个已登记回滚方案的依据**（「回滚 = 用回这份」），删了回滚路径就断了。删前先查该 `.bak` 名是否出现在任何技能/脚本/待办档案里，查不到引用才进清单。
- 包管理器缓存（uv / pip / npm / huggingface）：`~/.cache/uv/archive-v0`、`.cache/uv` 一类是**可重建资产**不是废弃垃圾——删后下次装包自动回填，处置最稳。汇报时写「可重建、删后自动回填」而不是「废弃」，并顺带给出体积（uv 缓存常见 2～3 G 量级，是删除类里少数能真正动水位的项）
- **webui 临时目录与散落报告文档**：`webui-bubble-<ts>` / `webui-docpreview-<ts>` / `webui-deck-<ts>` 等一次预览留一个的目录，加根目录下几十份 `报告-<ts>.docx`——零风险，但属**噪声级**（合计常仅几 MB），删前先按 §1c 掂量要不要走一趟授权
- 探针/截图产出目录里**混着大量空图或近空文件**（几十字节量级的 `.png`，无有效内容）：按体积排序时它们不显眼，但份数多时单独归一行报「N 份无效截图 / 合计 X」，别让它们藏在 `du` TOP 之外
- 已被现行状态取代的迁移/改名 tarball
- 模型缓存残留 tmp（形如 `.<name>_cache_<random>.tmp`，一次崩一个）
- 轮转旧日志 `.1/.2/.3`（**保留当前文件**，轮转链还是判据类的证据来源）

命中前先确认没有引用：`grep -rln "<名字>" <脚本目录> <cron 目录>`。**别动正在被写入的文件**，也别动别的 profile 的运行目录。

## 5. 提权到宿主的正确姿势

```bash
# ① 先确认密文取到了字节——取不到就别往下接线
/opt/data/.secrets/secret.py list | grep -i <关键字>     # 先核键名
/opt/data/.secrets/secret.py get <键名> | wc -c          # 字节数必须 >0
# ② 命令先落盘，再把执行权交给 root：命令不能直接管道进 sudo stdin（会被当密码读）
echo <b64> | base64 -d > /tmp/_c.sh
# ③ 密码走独立 stdin；sudo -S 藏在变量里会被硬拦
{ 密码; } | ssh … "sudo -p '' --stdin bash /tmp/_c.sh"
# ④ 落盘要核验
wc -c /tmp/_c.sh
```

`sudo: no password was provided` / `incorrect password` 几乎都是 ① 没验过（键名猜错、键不存在）而不是密码错。**不要据一次失败就断言提权通道不可用**——先列键名核对。

## 6. btrfs 上「目录变小」≠「分区腾出空间」

两种机制要分清，判据不同：

**(a) 快照子卷里的同名副本**：`du` 把快照目录算成独立占用，于是目录看着很大、数据其实只有一份。真增量只能用 `btrfs filesystem usage`（配 `filesystem df` 看重占用/共享）定性，需 root。得出结论前把快照目录标成「疑似副本，待 usage 定性」，别直接报成可回收空间。

**(b) 删除后空间不立即归还**：删掉的文件若仍被某个 subvolume 快照引用，目录实测降了、**`df` 却不降或只降一部分**。判据是**两个数对不上**——

```bash
du -sh <被清目录>          # 清前
# …执行 rm…
du -sh <被清目录>          # 清后  → 目录降了多少
df -h / | tail -1         # 分区降了多少  → 与上面差太远即中招
```

**报了「释放 X G」就必须两个数都核。** 只报目录实测会让主人以为分区已经腾出来了，下一轮水位纹丝不动时反噬成「这清理白做了」。遇到差额就如实说：目录已瘦身、分区水位短期不会变，别让他等一个不会来的变化。

## 7. 执行清理：批的是类别，不是范围

主人点头只批准了**他看到的那一类**。同目录下可能有别的可删项，但**没被列进清单就不在批准范围内**——「同属备份」不等于「主人同意删这个备份」。

执行顺序：

```bash
# ① 先验证正在用的那份是活的（mtime / 体积），再谈删旧件
ls -la --time-style=long-iso <活文件目录>/
# ② 只按清单里的那类筛，不要 rm <整个目录> 或宽通配
# ③ 删前先落一份清单存档（日后可追溯删了什么）
# ④ 删后双重核验：目录实测 + df（见 §6(b)，两个数可能对不上）
```

**删前那一步验证不能省。** 凭名字旧就删，很容易删掉正在写入的当前文件（本机 `state.db` 当天还在更新，而同目录旧快照看着一样）。

⚠️ **别用 `rm -rf <整个目录>` 兑现「清这个目录」**——目录里往往混着主人要留的东西（本机 `backups/` 删完快照后还剩 363M 的 tar.gz 完好）。**只删清单点名的那些项。**

## 验证
- 结论里每个数字都能追溯到一条实际命令输出；被排除的卷有显式说明
- 清理清单每项有路径 + 大小 + 「为什么可删」一句话
- 未获批准前 `du`/`ls` 只读，不执行任何 `rm`
- 执行后两个数都核：目录实测降了多少、`df` 降了多少（对不上照实说，别只报前者）
- 若第 1b 节的账对不平，结论里必须写明「清理只能缓解、不是解决」，免得主人等一个不会来的水位变化
