# 脚本开发纪律（跨平台通用）

## When to Use
- 新增/修改/维护任何 Python、PowerShell、Nodejs/mjs 脚本
- 更新技能模板、写 cron 脚本、批量任务脚本
- 调试脚本报错、输出被外部程序解析失败时
- 不适用于：轻量单命令（查状态、开关设备），直接走已有封装

**适用**：编写、修改、维护任何自动化脚本（Python / PowerShell / Nodejs / mjs）、技能模板、cron 脚本。不绑定特定主机。
**定位**：元规范，管"怎么写脚本"；与各领域技能（管"写什么"）正交。

## 受控产物目录（泛化）
只允许在目标主机的受控目录内创建/修改文件，禁止越界写：
- 本容器（Hermes）：技能 → ~/.hermes/skills/；脚本 → /opt/data/
- 远程主机A（Windows 11）：D:/agent-workspace（优先相对路径 ./；带空格/特殊字符路径必须加引号）
- 远程主机B（Windows 10）：D:/agent-workspace（与远程主机A路径一致）
- HA：/config/
可读取外部目录素材，但禁止在受控目录外创建/改写任何文件。需要子目录就在受控目录下新建。

## 优化类提案：先分清主人要的目标函数，再动手
主人说「优化一下 / 省点电 / 跑得太慢」时，**先确认他要的是哪一个指标，不要默认把「延迟」当「功耗」**——两者的正确杠杆常常相反。

- **提问优先于动手**：一次澄清「是想它更快，还是想它更省资源？」含糊时按省资源处理，并在方案里写明这是假设。
- **分清「成本大头」和「你以为的成本大头」**：动手前先量现状（进程累计 CPU、内存、调用频率、是否真的进入过低功耗状态）。若实测证明该项成本可忽略（如某常驻进程 39 天累计 CPU 仅 725 秒 ≈ 0.02%），就必须在方案里直说「这不是大头，收益接近零」——宁可推荐「不改」也不要交一份看起来很忙的方案。
- **每条优化单独判定，别打包成「全面提速」**：同一个系统里，「砍掉冷启动」省的是延迟，「拉长周期」省的才是唤醒次数，「让进程常驻」两者都不省。把几条混在一张表里会互相掩护错误结论。
- **若优化会削弱既有告警/兜底链路，先报这个代价再谈收益**，由主人决定取舍，不擅自牺牲告警时效换省电。

## 改造既有脚本前：先核对注释与代码是否一致
改一个你不熟悉的生产脚本（尤其带状态机和阈值判定的），先把注释、docstring、状态文件字段与真实逻辑逐条对齐：
- **注释描述的行为必须在代码里找得到**。找不到（如注释写「连续 3 次确认」而代码是单次触发）时，以代码实际行为为准改注释，并明确告知主人此前注释是错的。
- **删除死字段**：状态文件里存在但从不读写的键（如 `high_count` 只被写过、从没被读过）是误导源，一并清掉。
- 不要照着一份错注释做设计——后续所有优化都会被它带偏。

## 改造既有脚本：先取现场实测值，再定方案
- 采样间隔、阈值、调度周期这类「运行态参数」**一律以远端/现场实测为准**，不信脚本默认参数，不信历史印象，不信上一轮结论。取法：读日志相邻时间戳相减、查进程运行态、查配置实际值。
- 上一轮提过的结论**本轮重新验证**——环境会变（他人调过、计划任务重建会把参数打回默认值）。引用旧结论时标注它的取样时间。
- 若实测发现「要优化的项早已是优化后的值」，立刻停下并明说，不要重复优化已优化项：在主人眼里这等于没读现场。

## 改监控/采集链路：先列数据的消费者，再决定改哪一端

提议「别实时查了，改读本地缓存/日志快照」之前，先把这条数据的**所有消费者**列出来，并**逐字段核对快照是否覆盖报表实际展示的内容**——报表里的某些项常常来自另一条独立通道，压根不在你要读的那份快照里。

- **核对字段覆盖，不是核对「有没有这份数据」**：快照存在 ≠ 含有所需字段。实测一份传感器 JSONL 只含 CPU/Memory/GpuIntel 三类，而报表里的硬盘温度与风扇是另跑 WMI 取回来的；改成读快照会让这些项整体消失，且消失的是主人明确要求过的项。判据是对快照逐字段解析一遍，不是看文件大小和条数。
- **改采集端前先看谁在消费**：告警判定、报表推送、历史回溯可能共用同一份数据。拉长采样间隔会同时劣化告警时效——发现延迟变长，且「连续 N 次确认」这类按原频率标定的防抖窗口会跟着失真，改频率必须同步重标定参数。
- **主人用「有没有考虑到 X？」「你有没有发现 Y？」这类反问点出遗漏时，先停下手里的方案重新推导**，不要边改边补——这种反问通常指向方案的根本缺陷，不是细节遗漏。

## 改 cron 脚本前：先证明哪份副本真正被执行

cron 任务的 `script` 字段**只收裸文件名**，运行态唯一解析根是 `<hermes_home>/scripts`（default 即 `/home/agent/.hermes/scripts`）。`/opt/data/scripts/`、`/opt/data/` 根下的同名文件**永远不会被执行**——它们是影子副本，改它们等于空转，且现象极具迷惑性：行为完全没变，你会误以为是逻辑写错了、或把「周期性推送」误判成「自己测试误发」。

**判定分两级，先只读后探针：**

1. **只读解析（首选，秒级，不碰生产文件）**——直接问调度器自己的守卫函数，别靠肉眼推路径：

```bash
/opt/hermes/.venv/bin/python - <<'EOF'
import sys; sys.path.insert(0,'/opt/hermes')
from hermes_cli.cron import _scripts_dir_for_cron, _script_health_issue
print("运行态根 =", _scripts_dir_for_cron().resolve())
for s in ["todo_reminder.py", "../../opt/data/scripts/todo_reminder.py", "/opt/data/scripts/todo_reminder.py"]:
    print(f"{s:42} ->", _script_health_issue(s) or "OK")
EOF
```

   实测口径：裸名 `OK`；越界相对路径与绝对路径一律 `script resolves outside /home/agent/.hermes/scripts`。函数名带下划线、属内部 API，导入失败时降级为等价的路径数学：`realpath(scripts_root/名)` 必须仍在 `scripts_root` 内且 `isfile`。

2. **全量核对**：结构化遍历三份 `jobs.json`，逐条取 `job['script']` 判 `isfile`（勿对 `json.dumps` 输出跑正则，见 cron-overview 坑19）。一次盘点就能同时给出「引用数 / 缺失数 / 影子同名清单」。

3. **探针注入（仅当守卫函数不可用，或要证明某轮 tick 真的跑了新代码）**：给候选副本在 `main()` 前注入只写 `/tmp` 标记的一行（不改逻辑、不发卡片），等一轮自然执行后读标记；测完必须从**注入前**取的干净备份还原。

**收尾三条：**

- **绝对路径不是解法**：`cronjob_manage` 的 `script` 参数与运行态守卫**双重拒绝**越界路径，所以「把 `script` 改成绝对路径」这条老建议已失效——只能裸文件名 + 脚本真身放进 `~/.hermes/scripts/`（软链接同样被拒）。
- **影子副本新旧/大小不一致 ≠ 影子区是权威**：只读验证只能证明「两份不同」，判不出哪边功能更全。发现影子副本更新更大（如某脚本影子 13239B/较新，运行态 10889B）时，**只报分歧给主人裁决**，不要擅自拿影子覆盖运行态，也不要先删影子（它可能是唯一留存了那次改动的地方）。
- **改完必须复验**：再等一轮 cron，确认输出 `status=silent`（或预期行为），必要时读探针标记——证明新代码真的在跑，而不是又一次空转。

## cron 周期脚本的失败语义：预期失败必须静默

周期脚本（`no_agent` cron）的 **stdout 与退出码就是告警通道**：非零退出、超时都会被每个 tick 当成故障推送。所以「预期内的失败」必须自己吞掉并 `exit 0`，只留**一个**专门任务负责报错。

- **凭据/登录态失效属于预期失败**：多个任务共享同一会话时（如「每天续期」+「每 10 分钟轮询」），轮询任务遇到未登录/续期失败应静默 `exit 0`，由每天一次的续期任务报「需要重新登录」。否则 10 分钟一条，一天 144 条。
- **判据写进代码**：把共用的 `need_token()` 包在 `try: ... except SystemExit: sys.exit(0)` 里；上游 5xx/超时同样静默跳过本轮，等下一轮。
- **只有「不可恢复且需要人」才非零退出**：配置缺失、脚本自身异常、数据源结构性变更。
- **首次运行只建基线**：带状态机（地理围栏/去重/水位）的脚本，首跑必须写基线而不推送，避免上线即误报。
- **状态文件丢失要能自愈**：基线缺失 = 重新建基线（不是报错），否则容器重建后每轮都异常；会话文件丢失 = 提示重新登录，不伪造状态。
- **验收方法**：临时移走会话/状态文件各跑一次，确认「静默 + exit 0」；再手工翻转一个状态值，确认真的会输出一行。只跑成功路径验不出告警风暴。

## 多轮状态机脚本：场景注入测试与结构化判定

带状态机/会话的巡检脚本（地理围栏、行程卡、去重推送），单跑一次只能验「成功路径」，必须按**多轮注入**验收：

- **分支判据用结构化类型，禁止解析展示文本**：事件判定一律带独立 kind（如 `("unlock", "主驾门锁 已锁→解锁")`），不允许对渲染后的中文文案做子串判断——「解锁→已锁」（上锁动作）里也含"解锁"，`"解锁" in text` 会把上锁误判成行程起点，且测试和生产都不报错。展示文本只用于渲染。
- **多轮测试用持续演化的当前值 dict**，每轮在上一轮数据上 `update`（`cur.update(mut)`），不要每轮从同一个固定 BASE 重建——后者会造出物理上不可能的状态序列（解锁下一秒全锁），测出的失败是测试数据的锅，白改逻辑。
- **「持续 N 分钟」类判定必须锚定到会话起点，不能直接用跨会话的全局时间戳**：`last_move_ts`/`last_*_ts` 这类值是上一段会话的残留，车停了一天后一解锁，`now - last_move_ts` 直接 ≥ 阈值，立刻推出「停留提醒」且卡面行程起止同秒（`03:49 - 03:49`）。参考时刻取 `max(全局时间戳, session["started_ts"])`；卡面据此自检——**起止同秒就是判定锚点错了**，不是数据慢。
- **修这类误报要拿旧版对照复现，才算证明根因**：把脚本复制到临时目录，`fetch_data()` 改成读 `FAKE_DATA` 环境变量返回假数据、`STATE`/`LEGACY_*` 指向临时文件、加 `<PREFIX>_DRYRUN=1`；旧版（只还原问题行）与新版跑同一组注入——旧版复现线上那张错卡、新版不推，再补「真静止 21 分钟应推」「15 分钟前移动过不推」两轮断言。只验新版「不推」证明不了根因：不推也可能因为整条链压根没跑起来。
- **每轮都要断言**：静默轮真的零输出、开会话轮只写状态不推卡、封板轮卡片逐行核对（标题 + 时间线 + 附警）；最后补一轮「长期无事件」确认不会误推。
- **dry-run 开关（`<PREFIX>_DRYRUN=1`）与推送冷却字段分开验**：dry-run 只验证判定链路（卡片打到 stdout），冷却（如滞后告警 30 分钟）要在 dry-run 里改状态文件的时间戳单独验，别混在一轮。
- **测试 cleanup 只删自己新建的快照**：把生产状态文件一起删=基线重置，下一轮走 first 分支静默不推，看上去像「功能没生效」——清理前先确认文件是测试新建的还是生产在用的。
- **验证新增的捷径分支时，把旧判据构造为不满足**：新旧分支殊途同归（都封板/都推送）时，若测试场景里旧判据恰好先命中，「推卡了」的断言会通过但根本没走到新分支——捷径等于没测。给新分支专设场景：旧判据明确不满足（如确认期才过 1 分钟）+ 新分支条件满足；再补一轮「新分支条件也不满足 → 不触发」确认不会误触发。
- **断言里引用的产物变量必须先产出再引用**：检查清单不要在跑场景的调用参数里直接引用那次调用的输出变量（先跑后验两段式），否则 NameError 挡住的是测试而不是被测逻辑的问题。

### 数据源可能是陈旧的：判定前先过新鲜度闸门

轮询脚本读到的「设备状态」不等于「此刻的状态」。休眠设备（车机、电池供电传感器）只在被唤醒时上报，实测滞后 30 分钟到数小时；脚本若用本端运行时刻给数据盖章，这份滞后对外完全不可见。

- **闸门放在「整轮是否可信」这一层，不要只加在某一类事件上**：上报时刻缺失 / 解析失败 / 滞后超阈值 → 只更新基线，不生成事件、不判定、不推送。只给围栏或某条分支加闸门，其余分支照样被陈旧快照喂出事件。
- **时间戳一律记设备上报时刻**：`state["pos"]["t"] = now_ts` 会把 31 分钟前的定位标成「刚刚」，之后所有基于时长与新鲜度的判定全部失真。
- **解析失败必须落到「不可信」一侧**：`try: lag = now - parse(ts) except: pass` 会让 lag 停在默认 0，闸门反被放行。默认值取不可信那一侧。
- **阈值按判定粒度定**：事件判定用分钟级；小时级阈值只适合「整轮跳过」，不能拿来「照常判定」。
- **卡面标采样时刻并加 ≈ 前缀**：一个采样间隔内的事件顺序本来就不可知，别把同一采样帧的多个事件渲染成秒级精确。
- **混合时间线（采样推断行 + 权威精确行）渲染前必须按事件时刻全局排序**：两类行按抓取轮次追加，追加顺序≠时间顺序——精确的 07:07 点火会排在估算的 ≈07:09 解锁后面，读起来像时序错乱且数据核对时全是「对的」。每个事件 dict 记原始 ts，追加后原地排序；标题行、「最后动作」等一切取 `events[-1]` 的派生口径自动跟着正确。
- **长期不可靠的信号要退出控制流，不是调阈值**：某判据的数据源先天滞后（定位/围栏类），调阈值只是把误报频率换个数字，判错的性质不变。正确做法是把它从「封板/触发」条件里摘掉，降级成时间线事件与事后归因（如封板标题补「· 家中」），控制流改由可靠信号（里程增量、状态迁移）承担；同时在状态/文档里留一句「这条为什么不再参与判定」，否则后人调参时又会加回去。
- **闸门不得饿死终态确认**：「闸门失败只更新基线」只适用于开启新判定；已挂起的终态确认必须能在闸门失败路径完成——挂起已超确认期 + 当前快照与挂起时同态（如仍全锁）+ 增量/位移无增长 + 挂起后无位移证据 → 用旧快照直接确认封板。否则设备恰在触发事件后转入休眠低频上报，确认永远等不到新鲜数据，直到某次心跳偶然放行（症状：终态通知延迟数小时）。判据从「数据必须新鲜」换成「快照无新动作迹象」；若快照显示状态已变（如已解锁），仍不得封板。
- **抽共用渲染/封板函数时，返回的标题必须真接住，不能 `_` 丢弃**：收口函数同时返回 (标题, 行列表) 时，调用方若只接行列表、继续用本地旧标题，归因后缀（·位置）就只在一条路径生效——两条封板路径的卡片标题口径静默漂移且无任何报错（只有终验逐字段核对卡面才抓得出）。同一函数的每个调用点都要使用它的全部返回值；复验时标题与行列表逐字段断言，不只对行。
- **周期卡/封板卡的时间窗口结尾 = 最后事件时刻，不是本轮采样时刻**：用当前采样当结尾，会把事件之后的静置全算进窗口（卡面写「行程 20:42 - 02:15」而实际旅程 22:31 就结束了）。给每条事件维护时刻戳（`last_ev_ts`），封板行写最后事件时刻；结尾与推送间隔超过阈值时附一行「上报稀疏、封板延迟」说明，别让主人对着延迟数小时的推送猜原因。

### 对立事件的一次性判定：延迟确认，别当场下结论

同一状态可能对应两种语义（四门全锁 = 行车中落锁 / 停车闭锁），单帧快照分不出来。做法是挂起 + 下一轮用增量信号裁决：

- 首次命中 → 记 `pending` 与当时基线值（里程/位置），**不推送**。
- 下一轮：增量仍在增长 → 判「过程内事件」，撤销 pending，会话继续、不封板；增量不动且静置满阈值 → 判「终态事件」，推送并清会话。
- **单向硬证走快速通道**：如「车速 >0 绝不可能是停车闭锁」，这类信号只有假阴性没有假阳性，命中即定性，不必等确认轮。
- **权威精确事件源可用时，终态确认可走快速通道，但确认快照的采样时刻必须晚于该事件时刻**：消息层精确事件（如熄火）出现后，若本轮快照采样在事件之后且状态未变（仍全锁）、行车判据（增量/车速）未命中，可直接确认封板省掉固定静置等待。采样早于事件的快照可能是事件发生前的旧帧（如行车中落锁），拿它配刚到的熄火消息会把中途行程误封——此时退回普通延迟确认。
- **必须留撤销路径**：解锁要能撤销闭锁挂起，否则一次误挂起会把整段行程吞掉。
- **语义未验证的字段不参与判定**：取值含义没实测过（如引擎状态 2 到底是熄火还是运转）就写进能力边界，别拿它当判据。

### cron 轮询脚本必须自己防重叠

调度器不会等上一轮结束。网络慢或凭据续期时单轮可能超过周期，两个进程交错写同一状态文件 = 状态丢失且不报错。开跑第一步 `fcntl.flock(fd, LOCK_EX | LOCK_NB)`，拿不到锁静默 `exit 0`。

完整骨架（闸门 / 延迟确认 / flock / `main(data=None, now=None)` 可注入 / 场景注入测试模板）见 `references/polling-state-watch.md`。

**第一条测试命令就是打开 dry-run**：跑任何场景之前先 `export <PREFIX>_DRYRUN=1`（或等效拦截 `send_card`）——推送型脚本不设 dry-run 的首跑就是真发。理由：「这个场景应该不会触发推送」不成立，**场景判定写错了恰恰就会推**，而验证场景判定正是测试的目的；先把发送通道关死，再看判定结果对不对。

正确做法（三条都做，缺一不可）：
- **先设 dry-run，再跑场景**（见上条——顺序错了，第一轮注入就已经发出去了）。
- **备份必须在污染之前取**。测试中途才 `cp` 出来的 `.bak` 常常已经是改过的版本（实测拿一个值早已变成 `epoch 0` 的备份「还原」，等于没还原）。
- **同时拦截发送与写状态两个函数**，不是只拦发送：

```python
import host-b_monitor as m
m.send_card = lambda *a, **k: None   # 拦发送
m._save = lambda *a, **k: None       # 拦写状态 —— 只拦前者仍会落真时间戳
```

- 改状态文件前先想清楚：真写了当前时间戳，就等于凭空伪造一次告警历史，比不发更糟。

## 强制工作流（新增/改造脚本时必须遵守）
1. **环境确认**：不确定 Python/PowerShell 版本、已装包、真实路径时，先执行简短查询命令获取真实信息，禁止凭空猜测。
2. **模板复用**：优先从已有脚本中参考骨架结构（如 `/opt/data/scripts/` 下的成熟脚本），复制后填充业务逻辑，不从零手写全部代码。
3. **编码与异常规范**：
   - Python：头部 `# -*- coding: utf-8 -*-`；try-except 必须 `traceback.print_exc()` 打印完整堆栈，禁止裸 except
   - PowerShell：`$ErrorActionPreference = 'Stop'`；开启 UTF-8 输出编码；捕获并输出完整异常
   - Nodejs/mjs：捕获异常，输出完整错误堆栈
4. **静态前置校验**（先语法后业务，不直接执行）：
   - Python：`python -m py_compile xxx.py`（内置，无需安装）
   - PowerShell：`Invoke-ScriptAnalyzer xxx.ps1`（未安装时降级：`powershell -NoProfile -Command "$e=$null;[System.Management.Automation.Language.Parser]::ParseFile('xxx.ps1',[ref]$null,[ref]$e)|Out-Null;if($e){$e|ForEach-Object{$_.Message};exit 1}else{'OK'}"`，Parser::ParseFile 是内置 API，只做语法解析不执行代码）
   - Nodejs：`node --check xxx.mjs`（内置）
   - 工具缺失不硬卡流程：用上表降级方案，但必须在 stderr 注明"已降级校验"
5. **最小单元测试**：校验通过后先验证局部功能，再跑完整业务流程。

## 定点替换（patch）代码时的边界

按字面匹配替换代码时，**old_string 在语句中间截断，会把后半截留在原地变成孤儿续行**——当时不报错，下一次导入才炸 `IndentationError`（更阴的是语法仍合法、但语义悄悄变了）。

- **整句取、整句换**：目标跨多行（函数调用参数换行、链式调用、多行 dict/list 字面量）时，old_string 必须从语句起点带到收尾的 `)` / `]` / `}`，new_string 里也把整句补全；不要只替换「打开的头部」。
- **改完立刻对每一个被动的副本做静态校验**：`python3 -m py_compile <文件>` 逐份跑，不只看第一份。
- **多副本同一处改动收尾比 md5**：值一致才说明改动真落到了每一份；顺手 `py_compile` 反向确认没留孤儿续行。
- **先在一份上改完并校验语法，再推到其余副本**；不要把未验证的替换同时铺到 N 份文件里，那样报错也要 N 倍时间定位。

## 输出流硬性规则（极其重要）
1. 机器解析用 JSON → **stdout**（console.log / Write-Output / print 默认）
2. 所有人类可读日志、调试信息、提示 → **stderr**（console.error / print(..., file=sys.stderr) / Write-Error / Write-Warning）
3. 严禁普通日志污染 stdout，否则上层 JSON.parse 直接失败，造成静默故障
4. 拿到混杂日志的混合输出时，不能直接整体 JSON.parse；先截取 `{ ... }` JSON 块提取干净 JSON 再解析

## 统一错误结构与退出码
1. stdout 的 JSON 统一结构：成功 `{"ok": true, ...业务字段}`；失败 `{"ok": false, "error": "<人类可读信息>"}`
2. 进程退出码：成功 0，失败非 0（Python `sys.exit(1)`；Node `process.exitCode = 1`；PowerShell `exit 1`）
3. 上层解析流程：先看 `ok` 字段，再决定是否读业务字段；`ok=false` 时直接展示 error 并退出

## 调试排错强制规则
1. 优先执行命令拿真实运行证据：打印完整变量、原始返回字符串、完整对象，拿到日志后再做根因分析
2. 不靠脑补猜测对象结构、变量内容；拿不到真实输出不下确定性结论
3. 怀疑异常被吞：插入错误日志打印 → 复现 → 读取完整日志 → 定位 → 修改
4. 标准步骤：①插入调试输出 → ②复现问题 → ③读取完整日志 → ④定位问题 → ⑤修改代码
5. 多个可能性时逐个最小测试验证，不把全部假设堆在一起推演

## 量纲一致性：比较同类量前先对单位
阈值常量与被比较值**单位必须一致**，否则比较式会**恒真/恒假且不报错**——这类故障不抛异常、不打日志、看起来一切正常，只会让某个分支永远不走或永远走。

- 实测反例：采集函数返回百分比 `75.6`，阈值却按比例写成 `0.90`，`75.6 >= 0.9` **恒真** → 所有监控项全判「越限」，中间档（偏高）永远不触发，告警分级形同虚设。
- **写完比较立即干跑一次**：打印被比较值与阈值的实际值（`print(v, THRESHOLD, v >= THRESHOLD)`），用边界值（等于、略低于、远高于）各跑一次，确认三档都走得通——只测一个值会把恒真当正确。
- **同一语义的阈值出现在多处时**（采集端、体检端、告警端各一份），在每处都注明单位与源头，并在改一处时同步其余；两处口径漂移会让「A 说没事、B 说越限」互相打架，且两边都“看起来对”。
- 同型坑：同一数量用字节数与字符数混比（中文 UTF-8 一字 3 字节 → 虚高 63%）、同一时长用秒与毫秒混比。写跨模块比较前，先把两边的量纲写在同一行注释里。

## 接入上游第三方脚本：不改源码，包一层执行器再上线

主人贴来一个开源项目要求「装上跑起来/接进家里」时：**上游代码只读不改**，全部改动落在自己写的执行器里。选型与可行性评估走 `env-dependency-audit` 的「第三方开源仓库落地预评估」（含 GitHub 搜索 API 配方、假凭据干跑真入口）；本节管评估通过之后的上线动作。

1. **上游隔离**：上游 git clone 到 `<项目>/upstream/`，把当前 commit 写进 `upstream.commit`；升级只动这一个目录。执行器（`run.py`）、配置、状态、日志与上游平级，**永不混写上游文件**（否则下次 pull 冲突，也说不清错在谁）。
2. **依赖独立 venv**：`/usr/bin/python3.13 -m venv venv`（容器默认 `python3` 可能是 3.14 且不含 requests），上游依赖只装进这个 venv，不污染 Hermes 主环境。
3. **凭据从加密库注入**：执行器启动时读加密库键，注入子进程环境变量交给上游。上游原版把凭据写 GitHub Secrets / 邮件通知 / 明文配置的地方，就是这次的改写点（→ 加密库 + 飞书卡片），不要照抄它的凭据通道。
4. **凭据未就绪必须静默（armed 开关）**：配置放 `armed: false`，未启用时执行器打一行日志即 exit 0，**不预检、不推送、不标失败**。理由：上线当天凭据往往还没到（主人「登录晚点再弄」是常态），照常跑失败分支会在凌晨推一条无意义告警，且 cron 看门狗会把「未就绪」记成「任务坏了」。主人授权/登录后翻 true。
5. **退出码分诊**：`0` 成功/已完成/未启用、`1` 执行失败、`2` 凭据失效。cron 看门狗只能读状态与退出码，别让它靠 stdout 猜。
6. **stdout 分流**：执行器日志全量落 `<项目>/logs/YYYY-MM-DD.log`，由 `.sh` 包装重定向，cron 侧 `deliver=local`；结果通知由执行器**直调 `feishu_card.send_card`（有 True/False，可判失败重试一次）**。别把结果 print 给 cron 转投——会套英文外壳，且吞异常后判不出成败。
7. **通知静默策略写进 state.json**：成功每天一条；`already_done` 默认不推；凭据失效/执行失败按「结果变化立刻推 + 每 N 天重推一次」，否则凭据一过期就天天凌晨同一条。
8. **判致命要窄**：只有「非零退出 / 上游自报失败（如 `❌ 执行失败`）/ Traceback」才算整体失败；单曲、单文件的 ERROR 行只算提示——上游常把可跳过项也写成 ERROR，宽判会把部分成功报成整体失败。
9. **主人要的策略差异走「补丁入口」，不改上游源码**：主人对默认行为有偏好（评分档位、阈值、排序）时，别去改 `upstream/` 里的判断函数——在项目根写 `patch_main.py`：`sys.path.insert(0, upstream)` → `import` 自己的策略模块 → monkeypatch 上游那个函数（如 `Signer._get_score_and_tag`）→ 再 `import main` 跑上游入口；`cwd` 仍须是 `upstream/`（上游按相对路径与包名导入）。这样上游可随时 `git pull`，策略能单测、能回滚。**必须留自检开关**（如 `<PREFIX>_PRINT_STRATEGY=1` 只打印判定结果即退出）：没生效的 monkeypatch 会**静默沿用上游默认值**，跑起来看不出错，只有离线打印判定才能证明补丁真的挂上了。
10. **凭据类交付必须连「续期链路」一起交付**：cookie/token 都会过期，只接执行器不接续期，等于交付一个几周后必然报错的东西。续期优先用**平台官方登录流程写回加密库**（扫码 > 密码，密码登录风控更严），绝不让主人手动抠凭据（值进聊天记录即触凭据红线）。可复用实现 `/opt/data/music-partner/login_qr.py`（扫码 → 写库，状态码语义/备份要求见 music-downloader 技能「Cookie 续期」节）。

### 失败分支逐个注入验收（主人的验收标准）
交付「接好了」之前，给每个外部依赖留一个环境变量覆盖点，把失败变成可注入的：

| 钩子 | 作用 |
|------|------|
| `<PREFIX>_COOKIE_RAW` | 置空/伪造凭据，走「未配置」「凭据缺字段」「凭据失效」三条分支 |
| `<PREFIX>_PREFLIGHT_JSON` | 伪造预检结果，离线跑通「成功/已完成」分支而不碰真账号 |
| `<PREFIX>_UPSTREAM_DIR` / `<PREFIX>_PYTHON` | 换成必然失败的假上游，注入执行失败分支 |
| `--dry-run` / `--check` | 只打印卡片 JSON / 只读自检，两者都不发送、不写状态 |

最小矩阵（逐条干跑 + 抽取卡片正文核对）：**未配置凭据 / 凭据缺关键字段 / 凭据失效 / 成功 / 上游失败 / 今日已完成**。只跑成功路径不算验收；`--dry-run` 与自检不得写 state.json（会污染去重判定，导致真告警被静默）。

细节骨架与实测样例见 `references/upstream-script-onboarding.md`。

## 脚本生命周期与交付
1. **交付**：脚本完成后按用途落地——批量/一次性任务放受控目录对应位置（如 /opt/data/、技能 scripts/）；周期性任务挂 cron/schtasks；常用操作封装为已有风格命令（如 host-a_power.py 的 on/off/restart/status 子命令），禁止只留裸脚本
2. **归档**：临时文件走 tmp/ 生命周期，无需手动归档
3. **版本化**：多轮迭代保留最新版即可，旧版进 archives/ 或清理，除非主人明确要求保留历史
4. **更新索引**：新模板/新脚本落地后，同步在 SKILL.md 相关章节登记路径与用途

## Windows 平台特别注意
1. 路径反斜杠注意转义，字符串优先单引号，避免转义字符灾难
2. SSH 远程环境无交互式终端：脚本禁止 input() / Read-Host 等交互等待
3. 注意换行符、路径分隔符，不把 Linux 习惯直接套到 Windows

## 分级执行
- **轻量任务**（查状态、开关、单命令）：直接走已有封装脚本，不套完整重流程
- **新增/改造脚本、技能模板、批量任务**：走完整工作流（模板→静态校验→单元测试→全流程）

## 验证
- 脚本跑通后确认 stdout 只有机器可解析内容，人类日志全在 stderr
- 触发一次异常路径，确认堆栈确实打印、无静默吞错
- 检查退出码符合约定（成功 0 / 失败非 0）
- 幂等性：重复执行同一脚本不产生重复副作用（重复创建记录、重复发送、重复移动等）
- **验证完核对副作用面**：跑过测试就检查状态文件时间戳、推送流水表（`cron/deliveries.db`）、cron 执行记录（`cron/executions.db` 看 `delivery_outcome`）是否留下真实痕迹；有就照实说明并确认不会延续
- **误发推送后立刻自查并认下**：确认是哪一步写的、影响范围多大（后续运行是否已被静默推迟），别把「测试产物」含糊带过——主人看到的是一条凭空出现的卡片
